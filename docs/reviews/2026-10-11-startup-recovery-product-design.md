# 启动配置目录丢失/损坏修复 · 产品设计

日期：2026-10-11
调研依据：`docs/reviews/2026-10-11-startup-recovery-research.md`
状态：待 UI 设计稿审核后进入实现

## 1. 目标与约束映射

| 用户约束 | 产品规约 |
|---|---|
| 配置目录或文件不存在 → 按默认路径 `[用户目录]/.xaanink/` 自动创建并初始化，完成后自动进入应用（从新人引导开始） | F1 自动初始化（§4.1） |
| 目录存在但文件丢失 → 先尝试修复 | F2 自动修复（§4.2） |
| 无法修复 → 弹出对话框，[退出] 与 [重置配置数据] 两个选项；选后者清空原目录、重建并初始化，自动进入应用（从新人引导开始） | F3 恢复对话框（§4.3）、F4 重置执行（§4.4） |
| 避免出现只能退出、永远无法使用的情况 | F5 所有不可启动状态统一提供重置出口（§4.5） |

注：用户需求原文「充值配置文件信息 / 充值配置数据」按上下文理解为「重置配置数据」，按钮文案定为「重置配置数据」。

术语对齐：用户所说「配置文件目录」= 数据根目录 `[用户主目录]/.xaanink/`；另有一个 bootstrap 控制目录（`%APPDATA%\XaanInk`，Windows）存放指针与历史记录，用户不可见，重置时由实现一并处理。

## 2. 范围

**纳入**：默认数据根 `~/.xaanink` 的缺失/清空/文件损坏；bootstrap 指针损坏；初始化中断续跑；自定义数据根丢失时的死局出口；worker 启动失败（数据根相关错误码）的死局出口。

**不纳入**：

- 双品牌 bootstrap 冲突（`BRAND_BOOTSTRAP_CONFLICT`）：涉及 legacy 真实数据归属，保持现有错误框人工处理。
- 恢复已被用户删除的数据本体（做不到，也不承诺）。
- 迁移/恢复记录存在时的在途流程（继续走既有 maintenance / relocation 窗口）。
- 隔离测试根 `XAANINK_TEST_ROOT` 的行为变更。

## 3. 场景决策矩阵

「默认根」= `[用户主目录]/.xaanink`。优先级自上而下，命中即停：

| 优先级 | 条件 | 行为 |
|---|---|---|
| P0 | bootstrap 存在迁移日志/请求/恢复记录 | 保持既有 maintenance / relocation 流程（若该流程落入不可操作状态，按 P5 提供重置出口） |
| P1 | 指针悬空指向默认根，且默认根**缺失或为空**，bootstrap 除指针外无其他记录 | **F1 自动初始化**：无弹窗、无需操作，直接启动进入新人引导 |
| P2 | 默认根存在且非空，损坏属于链接级（R1 指针损坏 + 根完好；R2 marker 失效 + 指针与内容完好；R3 初始化中断且 id 一致） | **F2 自动修复**：无弹窗，修复成功直接启动 |
| P3 | 默认根存在且非空，损坏超出链接级（catalog 损坏、inbox 数据库缺失、id 不匹配、目录被替换、双边同坏等） | **F3 对话框**：[退出应用] / [重置配置数据] |
| P4 | 指针目标为**自定义**目录且丢失/失效 | 保持「定位原数据目录」窗口，并新增「重置配置数据」出口（F5） |
| P5 | worker 启动失败且错误码为数据根相关（`ROOT_STARTUP_FAILED` / `ROOT_INITIALIZATION_FAILED` / `MIGRATION_RECOVERY_REQUIRED` 等），或任何其它不可启动残留状态 | **F3 对话框**：[退出应用] / [重置配置数据] |
| P6 | 无指针、无记录、默认根完好（bootstrap 被系统清理） | 维持现状：`adopt()` 自愈，正常启动 |

## 4. 功能规约

### 4.1 F1 自动初始化

- 触发：启动分类命中 P1。
- 行为：主进程冷态（单实例锁持有、无窗口、无 worker）外科手术式移除 bootstrap 指针文件；随后走正常 `launch()`，worker 在空/缺失的默认根上执行既有初始化（marker → catalog → inbox → 数据库 → adopt 写指针）。
- 界面：**无对话框**。用户只看到正常启动，首次进入工作台后自动弹出新人引导（既有机制，`onboarding` 进度为 null 即触发）。
- 遥测/日志：不记录真实路径以外的任何用户数据；异常时降级为 F3 对话框而非错误框。

### 4.2 F2 自动修复

- 触发：启动分类命中 P2。
- 动作（主进程冷态，复用 `desktop/core` 校验原语，全程同步 lstat/realpath 复核、拒绝符号链接、原子写）：
  - R1：把损坏的 `data-root.json` 改名隔离为留证文件（不影响历史判定），由 worker `adopt()` 在启动时重建指针。
  - R2：以指针中的 `rootId` 重写 `xaanink-app.json`（`phase:"ready", inboxReady:true`），前置条件：指针完好、`catalog.json` 可解析、`inbox/` 与 `inbox/database/` 存在。
  - R3：marker `phase:"initializing"` 且 id 与指针一致时，跳过 relocation 闸门直接 `launch()`，由 `Workspaces.initialize` 续跑初始化。
- 修复后必须重新完整跑一遍启动分类 + preflight 验证；任何一步失败 → 撤销修复痕迹（隔离文件可保留），转入 F3 对话框。
- 单次启动只尝试一轮修复，不循环。

### 4.3 F3 恢复对话框

- 触发：P3 / P5，或 F1/F2 执行失败。
- 形态：复用 relocation 窗口的桌面外壳（隐藏标题栏、原生窗控、应用菜单、主题跟随系统），内容为本功能新设计的对话框（UI 设计稿 `design/startup-recovery/`）。
- 内容要素：
  - 标题：`无法修复数据目录`
  - 说明：`数据目录中的文件丢失或损坏，无法自动修复。可以退出应用保留现状，或重置配置数据后重新开始。`
  - 数据目录路径展示（默认根路径；自定义目标场景同时展示原目标路径）。
  - 按钮：`退出应用`（次要）、`重置配置数据`（主要，危险语义）。
- 点「重置配置数据」后进入**就地二次确认**（不另弹系统框）：
  - 红色警示区，如实列出后果：`重置会清空数据目录（<路径>）的全部内容，包括收件箱、设置与模型配置、作品索引和应用备份，此操作不可撤销。作品文件保存在各自的独立目录中，不会被删除，但重置后需要重新打开关联。`
  - 按钮：`返回` / `确认清空并重置`。
- 点「退出应用」：保持现状文件原样，退出。

### 4.4 F4 重置执行

- 环境：与 relocation 窗口相同的冷态隔离环境；执行前再次复核单实例锁、目录身份、路径等于默认根（realpath 相等、非符号链接）。
- 步骤：
  1. 清空默认根 `~/.xaanink` 内全部条目（目录缺失则创建）；**绝不删除自定义目标目录与任何作品目录**。
  2. 清除 bootstrap 控制/历史文件：`data-root.json`、`root-migration.json`、`root-migration-request.json`、`root-relocation-*`、`application-restore-*`（仅此五类，不动 userData 其余内容）。
  3. 完成后自动 `app.relaunch()` + `app.quit()`；新进程走 F1 路径初始化，进入新人引导。
- 进行中：界面显示 `正在重置数据目录…`，所有按钮禁用。
- 失败（如文件被占用）：显示 `重置未完成，请关闭可能占用文件的程序后重试`，提供 `重试` 与 `退出应用`；不留下半重置状态伪装成功 —— 半成品状态下重启仍会回到本对话框。

### 4.5 F5 统一重置出口（消灭死局）

- 「定位原数据目录」窗口在 `unavailable` / `cancelled` / `blocked` 三种相位均新增第三按钮 `重置配置数据`（危险语义，置于次要位置），点击后切换到 F3 的确认视图；确认后执行 F4。
- worker 启动失败路径（`index.ts` `failed()`）：数据根相关错误码不再弹 `showErrorBox`，改为打开 F3 对话框；非数据类错误（锁、旧版恢复记录等）维持错误框。
- 结果：任何启动失败状态下，用户永远有「退出」与「重置」两个可达动作。

## 6. 安全与完整性约束（实现必须遵守）

1. 全过程持有单实例锁；修复/重置只在无窗口、无 worker、无 session 的冷态执行。
2. 只操作两条固定路径：默认根 `~/.xaanink` 与 bootstrap 内五类控制文件；任何自定义目录、作品目录、其它用户文件都不在写入范围内。
3. 所有路径操作前 lstat + realpath 复核，拒绝符号链接；写操作用原子写（临时文件 + rename）。
4. 重置前必须把当前损坏的根留证隔离（改名而非静默覆盖已有文件）的场合仅限 R1 指针；重置清空是用户显式确认的破坏性动作，直接删除。
5. 真实数据与用户 Key 不进入日志与证据；测试使用隔离目录。
6. 默认无模型、无平台后备、无 HTTP 监听；修复/重置路径不引入网络访问。

## 7. 验收标准映射

| 验收标准 | 验证方式 |
|---|---|
| 默认根不存在 → 自动建目录、初始化、进引导 | 集成测试：隔离根模拟缺失，断言启动成功且 onboarding 进度为 null → 渲染端进引导（浏览器测试断言引导可见） |
| 目录在、文件丢失 → 先修复 | 单测覆盖 R1/R2/R3 修复与验证；集成测试断言修复后正常启动 |
| 无法修复 → 对话框两选项；选重置 → 清空重建 → 进引导 | 浏览器测试：对话框文案/按钮/二次确认/重置后重启；集成测试：重置后新进程全新初始化 |
| 不再出现只能退出的死局 | 场景矩阵逐条回归：worker 失败、blocked、lost 无副本等均有重置出口 |
| 通过所有测试 | `npm test` + `npm run test:core:evidence` + 浏览器测试 + 真实安装包手工验证 |
