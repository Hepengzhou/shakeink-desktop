# 配置目录任意删除自愈与兜底重建产品文档

日期：2026-10-15（经 197 独立审核修订）。依据：194 调研。与 188 R2 冲突处以本文档为准（历次修改以后者为准）。本文档约束配置目录（数据根）被任意删除/破坏后的启动行为。

## 总目标

无论配置目录中的文件被删除多少，应用都必须启动可用。能在归属明确、只增不删的前提下机械重建的，一律静默修复、用户完全无感；真正无法安全修复的，进入程序主界面后由用户在对话框中决策：清空全部配置数据并重建后重启，或直接退出。

## 行为规则

### R1 结构自愈（无感修复，直接启动）

以下缺失/损坏在启动时自动修复，不弹任何窗：

- `inbox/`、`inbox/database/` 缺失或形态异常（如 symlink、普通文件占位）→ 隔离异常项并重建空目录。
- `catalog.json` 缺失 → 写入空作品目录；损坏/形态异常 → 隔离为 `catalog.corrupt-<时间戳>.json` 后写空目录。
- 标记 `inboxReady:true` 而数据库缺失 → 隔离原标记（字节保留）并按原 id/app/phase 原子改写为 `inboxReady:false`；worker 随后自建新库并回写 `inboxReady:true`（`workspaces.ts:314-333` 语义）。
- 并发的指针不可解析 → 顺带隔离；标记缺失/可重建损坏且**有有效指针** → 以指针 rootId 重建。
- 已覆盖项保持不变：`state.json`（默认/隔离）、指针缺失或不可解析（auto-init/repair:pointer）、标记问题（auto-init/repair:marker/marker-new-id）、`drafts.json` 缺失（懒读）、`session/` 及缓存（自动重建）、`model-catalogs.json`（懒读）。
- 前提（安全红线）：归属明确（有效指针身份校验通过，或单一品牌标记有效且无冲突），目标是默认根目录，修复只增不删（除隔离重命名外不删除任何内容）。
- 坚守 dialog（进 R2）：品牌冲突（双品牌文件并存）、根身份不符（设备/inode 与指针不一致）、根为 symlink/非目录、**无指针且内容损坏**（无 id 来源，不铸新 id 覆盖不明内容）。
- reset 崩溃残留按「能修则修」优先：半清空根自愈为一致的空结构根（197 审核 P0-2 决策，修订 `startup-recovery.ts:170-172` 旧不变量注释）。

### R2 兜底清空重建（主界面 + 用户决策）

- 触发：R1 红线场景（dialog 分类）、R1 修复执行失败、worker 根启动失败。
- 流程：应用以系统临时目录下的**临时隔离数据根**启动真实主界面（空设置状态，可能呈现新用户引导，属正常；原配置目录保持原样不被触碰）→ 主窗口上弹原生模态对话框，文案明示：配置数据已损坏且无法自动修复；「清空全部配置并重启」将删除配置目录（完整路径）中的**全部文件**（**包括作品数据，不可撤销**）并自动重启重建；「退出」直接关闭应用、原文件保持原样。按钮：「退出」（默认/取消）、「清空全部配置并重启」。对话框或主窗口被关闭视同「退出」。
- 选「清空全部配置并重启」：删除该配置目录中的所有文件与 bootstrap 控制文件（复用既有 `executeStartupReset`，含目标路径校验）→ `app.relaunch()` 自动重启 → 全新配置自动重建 → 正常进入主界面。清空执行失败 → 错误对话框（原文件已保留）→ 退出。
- 选「退出」：`app.exit(0)`，原配置目录保持原样。
- 旧「受限恢复窗口」在以上场景由本流程取代；根迁移、根维护窗口属既有操作流程，不受影响。

### R3 可观测性

- R1 全程无感，启动时长与正常启动相当。
- R2 用户看到真实主界面 + 一个模态对话框，无错误框、无受限窗口；两次点击内完成清空重启或退出。
- 临时根残留于系统临时目录（运行期句柄不可删），由 OS 清理，不影响主流程。
