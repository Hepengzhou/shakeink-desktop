# macOS 发布实施方案独立审核

日期：2026-10-16。受审产物：[04-implementation-plan.md](04-implementation-plan.md)。审核范围为已批准问题分析的实施方案，不是实现或真实发布验收。

**结论：通过，无未关闭的方案阻断意见。** 用户已明确通过问题分析并授权实施；本方案仍应先通过用例审核，再进入 TDD。

## 证据与核查

核对了限定范围内的现有打包配置、入口、打包测试和已安装 v26 的签名、公证、归档及 blockmap 实现。本轮仅文件读取，未访问凭据、钥匙串、用户数据或启动应用；仅写本审核文档。

| 核查项 | 结论 |
| --- | --- |
| 变更边界 | 仅构建发布、最小签名权限和相关测试/文档；不改业务组件、IPC、存储、appId、产品名或 Web 来源。旧包、旧证据和原有未提交修改明确保留。 |
| 发布入口 | macOS 默认归档及 DMG/ZIP 走发布门；`--dir` 明确仅本地验包且不产归档。Windows 仍用原 NSIS 路径，强制 macOS 身份的条件不得扩散至 Windows。 |
| 身份与认证 | 仅有效 Developer ID Application，多个身份须明确唯一选择；Keychain profile 认证，无身份/认证前提即停，不产生可分发包。缺开发者资格和凭据的现实依赖已明确，未用自签名或模拟输出降低标准。 |
| `.app` 生命周期 | afterPack 完成资源与本地化后签名；已安装 `MacPackager.sign()` 内的公证调用在返回前由 `@electron/notarize` 完成 stapling；afterSign 检查可位于归档前，不需签名后修改业务资源。 |
| 原生签名与权限 | builder 的 `@electron/osx-sign` 递归发现并按路径深度由内向外签名；v26 `getOptionsForFile()` 可明确应用和继承 entitlement。仅 JIT，保留 renderer sandbox，不因加载失败预先广泛放宽权限；真实原生运行回归仍需执行。 |
| DMG 与最终元数据 | staging DMG 关闭中间更新信息，独立提交 Accepted 后附票据、验包，再从最终字节生成/核验 blockmap、大小及散列，避免旧 updateInfo。验完所有交付物才原子推广，失败不产生成功清单。 |
| 独立重验 | 重读清单并重算最终文件和 blockmap，重新执行 Apple 检查；不信任单一 passed 字段，不清除隔离属性，不运行应用。 |
| 验收口径 | 单元端口验证与真实签名、公证、目标系统分开；坏包只计负例。真实 DMG/ZIP 校验、干净 15.7.5 Apple Silicon 保留隔离的下载/安装/断网首启及业务回归均未被替代。 |

## 实现与后续审核必须维持的要求

- `asar:false` 下不能仅检查顶层 `.app`。需发现并逐个验证 Framework、Helper，以及 Resources 中 `.node`、`.dylib` 和无扩展名 Mach-O 的身份/Team 与签名，避免完整资源封印掩盖原生模块仍保留其它身份的问题；顶层与子项检查应相互补充。
- ZIP 在解压前检查原始条目名与链接目标/链接链，不允许条目或链接将写入引向临时目录外；允许 Electron Framework 需要的安全相对符号链接。解压后的 lstat/realpath 核验和信任校验不能省略。
- Windows 的原有不签名行为及资源编辑路径、`publish:never` 必须在真实配置生成用例中体现，不能仅靠文档声明。
- 验证发布前提不能暴露 profile/认证值；工具错误、超时及 Apple 拒绝不得回退为成功。

这些是方案已有“完整签名/归档安全/Windows保护/失败停止”要求的具体核查方式，不增加业务改动范围。下一阶段测试应直接覆盖对应遗漏和失败场景。

## 限定

本机缺少有效 Developer ID 身份及已设置的公证认证项，是当前真实发布验收依赖，不构成已满足验收。可继续代码修复和负例测试，但必须在真实身份、公证和目标环境检查全部通过后，才能声明本次修复完整完成。
