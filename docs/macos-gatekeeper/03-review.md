## 按严重程度排列的问题

### P2（已关闭）：补清 DMG 公证、附票据与最终 blockmap/updateInfo 的生命周期

位置：`02-analysis.md` 的“最小修复方案”第 3、4 项。

已安装 v26 的 `.app` 路径是 `MacPackager.sign()` → `notarizeIfProvided(appPath)`；`@electron/notarize/lib/index.js:46–49` 在返回前完成公证等待与 `.app` stapling。因此 `.app` 的票据可以在 DMG/ZIP 归档前完成。

但 `dmg-builder/out/dmg.js:44–55` 的实际顺序是 DMG 签名 → `createBlockmap()` → `artifactBuildCompleted`，没有 DMG 公证步骤。仅开启 `mac.notarize` 不会自动完成 DMG 容器公证和 stapling。若在 artifactBuildCompleted 或打包返回后附加 DMG 票据，DMG 字节会改变，而 builder 已经生成的 blockmap 和 updateInfo 仍对应旧字节。`differentialUpdateInfoBuilder.js:66–79` 还会先发送 blockmap 完成事件，不能把后续最终化直接当作原有更新元数据仍有效。

当前方案已要求“避免旧 blockmap”，但应明确可执行的阶段安排，避免实施时只重算 SHA-256 和文字发布记录。建议写明：`.app` 完成签名、公证和附票据后才归档；DMG 另设最终化阶段，公证和 stapling 后再生成或重建最终 blockmap、文件大小、SHA-512/updateInfo 等引用；中间元数据不得进入发布清单，最终验包失败则停止。继续保留 `publish: never`。也可采用等价且有源码/测试证据的正确阶段方案。

修正后，下一阶段用例应检查最终 DMG 字节与所有对外散列、大小和 blockmap 一致，覆盖签名/公证/stapling 任一步失败不会形成可分发清单。

### 复审记录

已重读修订后的 `02-analysis.md`“最小修复方案”第 1、3、4、5 项，核对结果：

- macOS 安装归档默认进入发布模式，本地 `package:dir` 与发布 staging 的用途明确；中间包不进入成功清单。
- `.app` 完成公证、stapling 和验证后才进入 ZIP/DMG，未将 `afterPack` 当成最终签名或系统信任验收阶段。
- DMG staging 明确使用 `dmg.writeUpdateInfo: false`；独立最终化阶段完成容器公证、附票据和验包，再从最终字节生成 blockmap、大小、SHA-512/SHA-256 及其引用，不复用中间 updateInfo。该字段与已安装 v26 `DmgTarget.build()` 的实际控制流相符。
- 公证失败、超时、票据无效与最终验包失败均停止推广；下一阶段用例覆盖顺序、元数据一致性和失败路径。继续保留 `publish: never`。

本项已满足方案阶段的修正条件。最终化脚本尚未实现，本复审只确认方案的阶段顺序和失败条件正确，不能替代实现后的真实产物一致性测试。
