# 启动写入锁/配置文件自动修复产品文档

日期：2026-10-15。依据：187 调研。本文档约束启动时「上次程序没正常关闭 / 写入锁」及配置文件异常的产品行为；界面文案除列明外不变。

## 目标

用户每次启动应用都能进入工作台。启动遇到可自行安全解决的问题（残留的已过世进程写入锁、中断的锁修复、损坏/缺失的配置文件）时，应用直接自行修复并继续启动，**不先弹任何对话框、不要求用户点击、不要求用户重新打开应用**；只有自动修复无法安全完成时，才把决策交给用户。

## 行为规则

### R1 写入锁自动修复（主规则）

- 启动检测到收件箱写入锁残留（上次进程异常退出）或上次修复中断的审计记录时：**不弹窗**，直接进入自动修复。
- 自动修复 = 现有「修复并退出」按钮的等价操作（`recover(true)`），仅移除残留锁并落审计记录；不更改作品、设置和草稿的任何字节。
- **最多尝试 3 次**；相邻尝试之间等待约 500ms（覆盖前一进程尚在退出收尾的瞬态）。任一尝试修复成功且复检确认锁已消失 → 直接继续正常启动进入工作台，无任何提示打断。
- 3 次全部失败 → 弹出**现有**「修复本地写入锁」对话框（文案、按钮不变），用户仍可手动「修复并退出」或「退出」；对话框内的修复结果提示与退出行为保持现状。
- 安全红线（沿用核心恢复闸，不因自动化放宽）：锁属主进程仍存活、属主位于其他机器、锁目录内容不明、审计记录被篡改——一律不修复，按失败计入尝试次数。

### R2 配置文件自愈（约束规则）

- 缺失的指针/标记/设置：按现状自动重建或落默认值（已具备，不变）。
- 可安全重建的指针/标记损坏：按现状自动修复（已具备，不变）。
- `state.json` 存在但损坏（无法解析或格式/校验不通过）：启动前将原文件隔离重命名为同目录 `state.corrupt-<时间戳>.json`（**原字节保留**，可人工找回），应用以默认设置继续启动；不弹窗。文件有效或未损坏时不得触碰。
- 归属不明的根数据冲突（`root-mismatch` / `content-damaged` / `default-invalid` 等 dialog 分类）、根迁移、根维护：**保留现有窗口**，由用户决策——这些场景自动选择有误清数据风险，不属于「能自己解决」。

### R3 术语与可观测性

- 「有文件锁」指本应用自建的写入锁目录（`.shakeink-lock` 残留），纳入 R1 自动修复；操作系统级文件占用导致的隔离重命名失败属 I/O 错误，维持现有错误框路径，不属于可自行解决范畴。
- 自动修复成功：用户无感知，启动时间与正常启动相当（最坏情况增加约 1s 的尝试间等待）。
- 自动修复全部失败：用户看到的对话框与现状完全一致，不新增文案。

## 验收映射

| 约束 | 落实 |
| --- | --- |
| 遇到写入锁直接自行修复，不直接弹错误对话框 | R1：先自动修复，3 次失败后才弹窗 |
| 能自己解决的自己解决，不等用户点「修复并退出」 | R1 自动 `recover(true)`；R2 配置自愈 |
| 最多尝试 3 次，全部失败后才弹对话框 | R1 尝试上限 3 |
| 每次都能正常启动，不因配置被改/破坏/缺失/文件锁/上次没正常关闭而无法启动 | R1（锁/异常关闭）+ R2（配置缺失/损坏）；归属不明场景按设计保留用户决策 |
